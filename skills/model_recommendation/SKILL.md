# 建模方案推荐（技能）

> 本技能的**唯一产物是一张"建议单"**（不是本体、不是结论页）。**推荐 ≠ 决定**：模型选择与"是否承担保鲜成本"由**人**拍板。
> 技能**只限模型、不限本体类型**：任何类/关系/数据属性一律 `ontology_types("<模型>")` **现查**，查不到就换，**绝不猜类型**。

## 0. 第 0 步：先问清三件事（不要先动工具）
1. **材料**：哪份（知识库文档 / 附件 / 表格 / 图 / 对话里零散说的）？
2. **意图**：要"抽成知识页"、"写规则判定"、"做流程梳理"，还是"先判断该不该建本体"？
3. **目标库**：建议单写到哪个库（默认「领域模型库」——D1：本体迭代方案与验证报告的载体）。

## 1. 判需求种类（**本技能第一件正事**）

按材料的**主导语义**选一条主路线（可并存，但必须写**主次**）：

| 需求种类（判据：材料里反复出现什么） | 主路线 | 模型/产物 | 现状 |
|---|---|---|---|
| **流程 / 岗责 / 审批 / 步骤**（谁→在何时→按什么步骤→产出什么） | **流程·EA 路线**（组织·角色·任务·步骤·活动·服务·系统·实体） | `ea` 类流程模型（**需新建**；可参考 `ontology/EA完整版.ttl` 作底稿，**不要直接恢复**——见"不恢复 ea"的口径） | ⚠️ `ontology/sources/` 现只有 `bmm.ttl`，ea 已退出编译 |
| **业务动机 / 政策 / 目标 / 规则约束**（为什么做、要达成什么、受什么约束） | **BMM 路线** | `bmm` 扩展（`DesiredResult`/`Means`/`Influencer`/`Assessment`/`Directive`） | ✅ 现有（30 类/37 关系/15 属性） |
| **智能体 / 技能 / 用例 / 工具调用**（谁来做、怎么调、用什么工具、产出什么） | **DDD + 智能体路线**（限界上下文 + Agent / Skill / MCPService / Tool / Task / Run / Artifact） | 新模型 `agent`（短名 ≤16） | ⚠️ **M1 裁决：先落任务库字段；模型到 P6 设计闭环再正式提方案** |
| **被评审 / 待交付的方案资产**（技术方案、部署、灾备、设备、技术栈） | **方案资产路线** | 新模型 `技术方案`(tsa)（P2 建） | ⚠️ 待建 |
| **结构化台账**（Excel/CSV 的字段语义） | 交给 **`structured_modeling`** 技能 | 类/数据属性/关系 | ✅ 现有技能 |
| **需求澄清 / 变更**（同一需求被反复修订） | 交给 **变更登记方案**（见策略文档"需求澄清与变更登记"节） | 澄清页 + 变更登记页 | ⚠️ 待建 |

> **判不出来的处理**：材料里多种语义并存时，**列出候选路线 + 各自的证据句**，让用户点一条为主；**不要替用户拍**。

## 2. 材料画像（只读）
- `get_document_info` → 文档类型 / 切片数；
- `doc_outline(kb_id, knowledge_id, budget_tokens=…)` → 章节骨架 + **图/表位置**（表 → 记下转 `structured_modeling`；图 → 记下转多模态）；
- `list_knowledge_chunks` / `grep_chunks` → 抽样正文。

## 3. 概念候选抽取（每条必须带原文依据）
按 6 类抽：**对象 / 规则 / 过程·活动 / 组织·角色·人员 / 资源·系统 / 实现（智能体·技能·工具）**。
输出候选表：`概念 | 类别 | 出现位置 | source_text（原句） | 频次`。
> 抽不到原句的**不要报**（宁缺毋滥）；拿不准的进"待确认"。

## 4. **消费关系判定**（本技能的核心判据，与"规则用知识的 triage"同一把尺）

对**每个候选概念/知识项**追问：**将来谁消费它？** 判据（J1-J7 + 消费者 + 保鲜成本）：

| 消费形态 | 判定要点 | 落点 |
|---|---|---|
| **被"技能"在流程里读取**（如规则判定要读的知识） | 必须结构化、可查询、可复算 | **L1**（本体类/属性/词表） |
| **被"智能体"作为检索/引用源**（需求溯源、验收、评测的源头） | 必须有**稳定身份 + 证据链**（`source_text`/坐标/置信度/人工确认） | **L1 + 证据字段** |
| 只被人读 | 无机器消费 | **L2**（wiki 页） |
| 只被"最终落地产物/表单"存 | 属业务数据 | **任务库/业务表** |

两条硬规矩：
1. **"知识"与"最终落地产物"是两类对象**（知识被消费，产物是消费的结果）——但两者之间**必须有消费关系**：`技能/智能体 --consumes--> 知识`、`产物 --derivesFrom--> 知识`；**建议单里必须画出这条边**，否则该知识不该建。
2. **每个 L1 项都要写"消费者"**（哪个技能/哪个智能体/哪条规则/哪份产物）。**写不出消费者的，降级 L2 或走任务库**——这就是"防本体膨胀"的门槛（与需求侧"按规则需要的知识"同一标准）。

## 5. DDD 定位与"要不要新建/恢复模型"的判定

先给每个概念定**限界上下文**（核心域 / 支撑域 / 通用·实现域），再定**模型动作**：

| 模型动作 | 何时用 | 代价 |
|---|---|---|
| **命中现有类（复用）** | 概念在 `ontology_types("<模型>")` 里已有等价类 | 0 |
| **扩展现有模型**（加类/属性/词表） | 概念在该模型**语义边界内**（如"角色"→词表、"总结"→执行级别） | 小：TTL 加条目 + 重编译 + 写影响面 |
| **新建独立模型** | 概念属**另一层**（实现运行时 `agent` / 方案资产 `tsa` / 流程 `ea` 类） | 中：新 TTL + 短名(≤16) + 目录 + 页 |
| **不建**（任务库/业务表/指针） | 过程数据、版本号、表单字段 | 0 |

三条口径（必须写进建议单）：
- **跨层只桥接、不继承**：实现层**单向引用**业务层（`agent:X -[:bmm:realizes]-> bmm:Means`）；
- **owning model 唯一**：一个概念只有一个真源，别处只放引用（教训：`客户` 曾在 `ea:Customer` ↔ `bmm:Resource` 间 retag 拉锯）；
- **"恢复 ea"不是默认动作**：只有材料**主体是流程/岗责/审批**（判据：角色—步骤—产出成链）才建议**新建流程模型**（可用 `ontology/EA完整版.ttl` 作底稿），并在建议单里**明写与 bmm 的边界**（谁拥有"系统"、谁拥有"角色"）。

## 6. 组织类概念（角色 / 人员 / 岗位）—— **在本技能内评估，不预设**

| 概念 | 先看现有 | 若无等价则建议 | 落点 |
|---|---|---|---|
| **角色**（组长/专家/岗位） | `bmm:OrganizationUnit` 是**机构**；角色是**职责位** | **词表**（如 `bmm:ReviewRole`）或 `OrganizationUnit` 的**职责枚举属性** | 词表/属性 |
| **人员** | `bmm:OrganizationUnit`（`bmm:assessedBy`/`createdBy` 的 range **已是它**） | **复用** OrganizationUnit 实例；**不要**新建 `Person` | 复用 |
| **履职/核实动作** | `bmm:Assessment`（`assessedBy`→OrganizationUnit，`minCardinality=1`） | **复用** | 复用 |

> 口径：**能用词表/属性表达职责的，就不建类**；**能复用 OrganizationUnit 的，就不建 Person**；最终仍由建议单 + 人确认（M3 口径）。

## 7. 覆盖度比对（类型一律现查）
- `skills()` 看**技能面**（哪些技能已在做这件事，它们的 `models`/`tools` 是什么）；
- `ontology_types("bmm")` 等**逐个模型**取类/关系/数据属性（含 `requires`/`affects` 依赖线索）；
- `context_scan`/`context_lookup`/`context_page` 看**跨库上下文映射**是否已有约定；
- 对每个候选概念标：**命中 / 需扩展 / 需新建模型 / 不建**。

## 8. 外部参考（你要求的"LLM 知识 + 网络搜索 + 知识检索"）
1. **本库既有约定最优先**：`wiki_search` / `wiki_read_page`（避免与存量冲突）、`service_overview`；
2. **LLM 知识**对标框架：BMM（动机）/ DDD（限界上下文、聚合）/ TOGAF·ArchiMate（流程·应用·技术分层）/ 用例驱动；框架名要**落到具体类/关系/词表的建议**上；
3. **网络搜索**：智能体若开了 `web_search`/`web_fetch` 才用；**内网不可达就标"未获取"，绝不编造**。

## 9. 建议单（唯一产物）+ 落库

| 概念 | 需求种类/路线 | DDD 定位 | 建议动作 | owning 载体 | **消费关系（谁消费）** | J1-J7 | 保鲜成本(f×h) | 反例 | 置信度 | 原文依据 |
|---|---|---|---|---|---|---|---|---|---|---|

另附三段：**① 不建清单**（+ 落哪个库/表）｜**② 新增清单**（模型/类/词表 + 最小闭集 + 影响面）｜**③ 待确认清单**（证据不足/需业务拍板）。

- 用 `save_knowledge`（**必须显式 `mode="apply"`**；先 `dry_run` 念清单给用户确认）把建议单落到**领域模型库**；跨上下文引用先 `link_candidates` 登记、确认后 `resolve_link_candidate`；
- 涉及类型迁移先 `retag_preview` 看影响面；
- 收尾 `audit_scan`（建议单页也要有原文依据）。

## 纪律
1. **类型现查**：`ontology_types` 查不到就换，**不猜、不自造**。
2. **每条建议必须有 `source_text`**；无依据的进"待确认"。
3. **推荐 ≠ 决定**：模型选择 / 是否承担保鲜成本由**人**拍板（策略 §2.2 决策卡）。
4. **一次只推一个材料**，跨材料分单出（便于对比）。
5. **不写实现**：不写代码/SQL/表结构；只写"概念 → 模型/路线"的映射与理由。
6. **不落本体**：本技能只落"建议单"（需求建模结果）；落本体是 `domain_modeling` / `structured_modeling` / 人工编译的事。
