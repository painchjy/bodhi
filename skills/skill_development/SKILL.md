# 设计开发（技能）

> **本技能由「设计开发智能体」使用**：把"领域建模产物 + 知识需求"变成**可运行的业务智能体与业务技能**。
> 与领域建模智能体的分工：**领域建模智能体管内容（知识/本体），本技能管实现（智能体/技能/工具/安装）**。
> **越界规则**：**不改本体**（不新增类/属性/词表）；需要本体 → 只写**改进建议**（`adviceCategory=本体类`）。

## 0. 第 0 步：问清四件事
1. **要开发什么**：业务智能体（一个入口 + 技能面）／业务技能（`SKILL.md`）／工具（MCP，通常先挡板）；
2. **服务的业务目标**：用一句话写清"它替谁做什么判断/产出什么"；
3. **目标库与租户**：技能与知识页写到哪个库、哪个租户；
4. **投产边界**：**哪些工具现在没有**（= 需要挡板的清单）。

## 1. 输入（从哪来，不要凭空造）
- 领域建模产物：`model_recommendation` 的**建议单**、`domain_modeling` 的**知识页**、`session_provenance` 的**会话页/改进建议**；
- 需求原文（`doc_outline`/`grep_chunks`）与现有规则（`rules_of_policy`）；
- **现有技能目录**：`skills()`（先看有没有现成的，能用就不新造）。

## 2. 设计（**先出设计单，不写文件**）

**A. 业务智能体设计单**
| 项 | 内容 |
|---|---|
| 名称 / 触发 | 何时启用（用户说法、事件） |
| 角色与目标 | 一句话"替谁做什么" |
| 技能面 | 用哪几个技能（**单一来源**，改技能不改智能体） |
| 工具面 | 用哪些 MCP 工具（**逐个标 `已投产 / 挡板`**） |
| 工作知识库（清单） | **只列运行时要读写的工作知识库**：库名 + 用途（写什么/读什么）+ 读写方式。**不要列领域知识库（本库）**——它由**部署提示词上下文**表达（与设计/部署保持一致，不需要额外配置管理）。技能/工具用这份清单限定**目标库范围** |
| 人机分工 | 哪些必须人工确认（`dry_run`/人工协助子任务） |

**B. 业务技能设计单**（每个技能一张）
`id` / `name` / `when` / `models`（**只限模型、不限类型**）/ `stages` / `tools` + **步骤** + **输出契约** + **门禁** + **消费者**（谁用它）。

## 3. 脚手架（scaffold）
- 产出 `skills/<id>/SKILL.md` 文本，交给用户**确认 diff 后再写盘**；
- **硬要求**：front-matter **所有值写在单行**（`tools:`/`stages:` 用 `[a, b, c]` 同一行）—— 因为容器兜底解析器 `ke_yamlmini` 是**逐行**的，跨行会让 `tools` 退化成字符串（`document_review` 已有此问题）；
- 正文结构照现有技能：`## 0 第 0 步` → `## 1 主流程` → `## 输出契约` → `## 纪律` → 收尾 `audit_scan`；
- **不改其它技能**；技能**不写本体类型清单**（类型一律 `ontology_types` 现查）。

## 4. 配置与安装指引（install，交付给业务方自验）
必须包含 5 项：
1. **依赖**：MCP 服务注册/重启（`skills()` 会列出新技能）；所需 Python/网络；
2. **技能安装**：把 `skills/<id>/SKILL.md` 放到技能目录即生效（**无需注册智能体**）；如需沙箱 bundle 另说明；
3. **库与模型配置**：知识库绑定、`models`/`default_model`、租户与权限；
4. **工具状态表**（关键）：每个工具一行 —— `已投产 / 挡板(stub)` + **影响的结论类型** + 数据是否打标；
5. **验证步骤**：业务方照此能**独立跑一轮**并判断结论是否可信（含"模拟数据"如何识别）。

## 5. 挡板计划（stub，与框架 §7-F 一致）
- **契约先行**：先写接口契约（入参/出参/错误/字段含义），挡板与真实实现**共用**；
- **打标**：挡板返回 `_mock: true` + `_source: "stub:<工具名>"`；引用它的结论必须显示**"模拟数据"**；
- **不污染**：写库/发布类挡板**默认 `dry_run`**；
- **可切换**：`MOCK_TOOLS=1` 或每工具 `mock=true`，**换实现不改调用方**；
- **可追溯**：替换留一条会话页 + 一条改进建议（`adviceCategory=工具类`）。

## 6. 验证（verify，交付"一轮完整评估"）
- 业务方按 §4-5 的清单跑一轮：结论页/问题**带来源定位**、模拟数据**带标**；
- 收尾 `audit_scan`（无来源即 F3 红）；
- 产出**改进建议**：`技能类`（技能步骤/门禁问题）、`工具类`（契约/挡板→真实）、`知识类`（知识缺/过期）、`本体类`（缺类/缺属性）。

## 纪律
1. **不改本体**；需要本体 → 只写建议。
2. **先设计单 → 人确认 → 再写文件**（不越过用户直接落盘）。
3. **front-matter 单行值**（兼容无 PyYAML 的容器）。
4. **只限模型、不限本体类型**；类型 `ontology_types` 现查。
5. **每个技能/工具都要有消费者与验收口径**；写不出消费者的，不建（防膨胀）。
6. **不写实现细节**（不写 SQL/表结构/接口参数实现）；工具实现属"先契约 → 挡板 → 真实"三步。
7. **落库铁律（2026-10-04）**：写页用 `save_knowledge(..., model="agent", session_no="<运行时给你的会话编号>", mode="apply")`——
   - `session_no` **必传**（WeKnora 会话 uuid）：服务端据此取「**会话选择的智能体**」注 `agentName`、取租户名注 `tenantName`，并给本次**所有页**自动挂 `bmm:sourceSession`；
   - **取不到会话身份 → 工具拒绝写库**（回执 `need_session=true` + `reason`）：此时**不要自编编号、不要换库、不要跳过**，向用户说明"需要运行时把会话编号传给我"；
   - `agentName`/`tenantName` **不要自己写**（写了也会被服务端覆盖）。
