# 知识运维策略 + 技能群方案（以《技术方案评审》需求做 PoC）

> 日期：2026-10-01 ｜ 状态：**待确认的草案**（本文档未提交 git）｜ 配套：`docs/ontology-rebuild-analysis.md`
> 目标不是"实现一个需求"，而是**用这个需求摸索出一套可复用的知识运维方法论**，并把方法固化成**技能群**，最后在本需求上做**概念验证（PoC）**。

## 0. 一句话主张

> **不是所有知识都该进本体，但"决定推理结论的知识"必须进本体。**
> 本体化的判据是**推理确定性**（而不是"有没有结构"）；其余知识按可追溯性/权威性分别落到 **wiki** 或 **原始载体**。
> 并且：**重点规则走双轨**（纯自然语言 vs 本体规范化）**做 A/B**，用数据说话"本体到底值不值"。

## 1. 知识运维策略：三级分层 + 可执行判据

### 1.1 三级载体

| 级别 | 载体 | 典型形态 | 用途 |
|---|---|---|---|
| **L1 本体化**（Ontology-grade） | 图谱（TTL→Neo4j）+ 本体规范页 | 类/关系/受控词表/实例 + 证据 | **机器判定**、跨对象比较、聚合、影响分析 |
| **L2 Wiki 化**（Wiki-grade） | wiki 页 + 证据引用（`source_refs`） | 自由文本 + 章节定位 + 来源 | **人读 + 可追溯**；结构不稳定或无需判定 |
| **L3 原始载体**（Raw-grade） | 原文档/图纸/表格/业务库**本身** | 只登记"出处指针"（文档 id + 章节/页码/图坐标） | **按需检索**，不复制、不保真损耗 |

> 关键点：**L3 不是"没管"，而是"登记指针 + 按需取用"**（`reference_lookup` / `doc_outline` / `grep_chunks` + 坐标）。权威源在外部系统（如 IT 工作平台的认证清单）时，L3 是正确选择。

### 1.2 判据（打分卡：任一命中 → 倾向 L1）

| # | 判据 | 命中含义 |
|---|---|---|
| J1 | **推理确定性**：同一输入必须给同一结论 | 规则判定、合规校验 |
| J2 | **跨对象关联**：结论依赖多个对象/多份文档 | 问题↔规则↔章节↔系统↔部署 |
| J3 | **需要比较/计算**：等级 vs 要求、版本 vs 清单、现状 vs 目标 | 阈值/矩阵判定 |
| J4 | **需要聚合**：如"哪些系统违反 X" | 统计与看板 |
| J5 | **机器可执行**：要作为查询/脚本/规则引擎的入参 | cypher / py / 规则表 |
| J6 | **身份唯一稳定**：系统编号、云名、等级等需要唯一识别 | 消歧与复用 |
| J7 | **生命周期稳定**：结构变化频率低（月/年级） | 值得投入建模 |
| — | 反向（倾向 L2/L3）：一次性使用、频繁变化、本质是**裁量/判断**、权威源在外 | 不做本体 |

**判据用"打分而非拍脑袋"**：每条 0/1，L1 建议阈值 = **≥2 条命中且含 J1 或 J3**；否则 L2/L3。（阈值可调，PoC 阶段校准。）

### 1.3 知识会**升级/降级**（运维的核心动作）

```
草案(wiki) --结构稳定+需要判定--> 本体化(L1)      升级
规则退役 --不再参与判定--> 归档 wiki(L2)          降级
权威源更新 --外部为准--> L1 缓存条目刷新          同步
新知识 --不知归哪--> 先 L3 指针 + L2 一页，PoC 后再定  渐进
```
> 每次升级/降级都要留**依据与影响面**（谁引用了它、页面/图谱怎么变），这就是"知识运维"，也就是技能 S6 的职责。

### 2.2 前置知识的决策框架：**是否需要本体 × 保鲜成本 × 收益**（按你的反馈）

> 前置知识（外部事实、映射表、清单）**不是越多越好**：本体化能提置信度，但**要有人维护**。所以每一项都走这张卡，由**人**决策；A/B 只负责提供"收益"侧的实测数据。

**决策卡字段（每项前置知识填一行）**

| 字段 | 含义 |
|---|---|
| ① 更新频率 f | 权威源多久变一次（次/年） |
| ② 单次维护工时 h | 含核验 + 回归（人时） |
| ③ 权威源是否机器可读 | 能否自动同步 |
| ④ 失效后果 | 会导致误判 / 漏判吗（高/中/低） |
| ⑤ **A/B 边际收益 Δ** | 本体轨 − 纯 NL 轨（正确率 / 证据可回溯率 / 外部知识依赖数）→ **由 P5 实测回填** |

**判据**：`年成本 ≈ f × h`；`性价比 = Δ ÷ 年成本`
- **Δ ≈ 0（A/B 差异不大）→ 不本体化**（留 L2 或 L3 指针）—— 这条正是你要的"差异不大就由人决定不增加本体/不承担保鲜成本"；
- Δ 明显 > 0 且成本可接受 → **本体化（L1）**；
- Δ 大但成本也大 → 折中：**只建指针 + 带有效期的缓存**，人工兜底。

**本需求 4 个候选项（先验判断，待 P5 的 Δ 收敛后由你拍板）**

| 候选前置知识 | 需要本体？ | 保鲜成本（估） | 收益（估） | 建议 |
|---|---|---|---|---|
| 系统等级 → 最低要求绑定 | 需要 | **低**：随行内制度变，约年更 1 次 / 1 人时 | **最高**：R1 判定的核心 | **本体化（L1）** |
| 云名 / 机房名 → 地区（~10 条） | 需要 | **低**：新增云/机房才改，f<5/年、0.2 人时 | **高**：决定"同城/异地"结论 | **轻量本体 + 允许名称推测** |
| 认证清单（产品/版本/有效期） | 需要（否则无法比对版本号） | **高**：IT 工作平台持续滚动、版本频繁 | 中高（只服务 R2） | **只建指针 + 带有效期的缓存**，不复制全量 |
| 历史方案里的"现状部署" | 可选 | **中高**：需从历史方案抽取并持续保鲜 | 中（影响"变更→设备申请一致性"） | **本期不建**（先用方案内背景），PoC 后按 Δ 再定 |

> 这张卡就是"**本体化与运维成本由人决策、由 A/B 提供依据**"的落地形态（对应你第 2 点）。

### 2.1 三个库的角色与**两个闭环**（依据你的 D1 裁决）

> **⚠️ 2026-10-01 修订（知识库分类）**：本节原按"三库"描述；现按你的裁定改为 **两类闭环共 3 类知识库（不可混用）**：
> ① **特殊库（`.env` 注册）**：企业本体模型（手工上传维护）／企业共享概念模型（**运维智能体维护、其他智能体只读**，= DDD 上下文映射载体）／企业知识管理领域（知识提取/管理技能与工具，**暂不纳入两闭环**）
> ② **领域知识库**：领域建模目标库 + 业务智能体/技能/工具/评估/改进建议的**定义库**（**业务智能体不得把它当工作知识库**）
> ③ **工作知识库**：业务智能体运行时读写（运行产物），**范围由领域知识库指定**
> 完整表（含实测库 id）与 DDD 处理见 `docs/cases/技术方案评审/two-loops-framework.md` **§7-G**。

| 库 | 角色 | 放什么 | 不放什么 |
|---|---|---|---|
| **企业本体模型库** `08810cbd-…` | **本体真源**（词表/骨架） | 模型/类/关系/属性（TTL 编译投影）：`bmm`、`技术方案`、规则的**类**与受控词表 | 具体技术方案、运行过程数据 |
| **技术方案评审领域模型** `7efad3eb-…` | **需求建模结果**（需求↔实现的闭环载体） | ① 规则实例；② 智能体的**目标**；③ **方法手段**（技能/工具/存量 API 整合）；④ **影响因素**；⑤ **评价**；⑥ **本体建模迭代方案 + 验证报告** | 被评审方案的事实（在任务库） |
| **技术方案评审任务知识库** `12ccea38-…` | **技术方案实例 + 任务运行结果** | ① 被评审的技术方案实例（系统/等级/部署/灾备/技术栈/设备/图证据）；② 轮次/问题/专家核实/修改溯源；③ **A/B 效果数据** | 本体定义、需求建模产物 |

```
┌─ 业务闭环（跑起来 → 改得更好） ─────────────────────────────────────┐
│  任务库：技术方案实例 → 评审运行 → 结果（问题/核实/A-B 效果）          │
│        └────────► 反推「领域模型库」里的智能体与技能设计改进           │
└──────────────────────────────────────────────────────────────────┘
┌─ 设计闭环（需求变 → 本体演进） ────────────────────────────────────┐
│  需求变更（如新增规则）                                                │
│    ├─ 不增加本体就能满足 → 记录「不本体化」的决策与效果（L2 轨）        │
│    └─ 或需要本体做 A/B 验证 → 反推「企业本体模型库」的本体迭代          │
│  迭代方案 + 验证报告 → 记在「领域模型库」→ 本体变更有据可查、可回滚    │
└──────────────────────────────────────────────────────────────────┘
```

> **由此得到 PoC 的落点**：`技术方案`（tsa）那套类/词表进**企业本体模型库**；本次的**规则实例与判定式**、以及**双轨 A/B 的验证报告**进**领域模型库**；两份部署图识别出的方案事实进**任务库**。
> **单一真源提示**：若把规则实例作为**本体个体**写进 TTL，编译会自动投影到企业本体模型库 → 与"规则实例住领域模型库"存在**双写风险**。我的处理：**TTL 是真源（本体个体）**，领域模型库里放"需求建模视角的规则条目"（知识需求/判定式指针/评价/迭代报告，指向该个体）。此约定待你在 P2 前确认（见 §8 附注）。

## 3. 规则侧设计：规则本体（metamodel）+ 双轨 A/B

### 3.1 规则本体（草案，挂在 `bmm` 或独立 `rule` 模型 —— 见 D2'）

```
:BusinessRule                ← 已有（bmm）：NL 描述 + 执行级别 + 适用范围（现状）
:RuleCondition               ← 新：条件（三形态：自然语言 / 结构化谓词 / 判定式指针）
    数据属性：kind(nl|structured|check) / expression / target(对象类型) / operator / threshold
:RuleKnowledgeNeed           ← 新：判定该规则**必须先提取的知识**
    数据属性：needType(系统等级|部署方式|灾备方式|云|机房|设备|技术栈|版本|RTO|…) / required(bool)
              sourceHint(文档章节/表格/图) / confidenceThreshold
:RuleCheck                   ← 新：可执行判定式（只读）
    数据属性：impl(nl_llm|graph_query|rule_table|python) / artifact(cypher/py/表) / version / lastVerifiedAt
:CheckResult                 ← 新：一次判定的结果（可复算、可复核）
    数据属性：verdict(pass|violate|unknown) / evidence[] / confidence / humanConfirmed / runAt
:IssueSeverity               ← 受控词表（严重/一般/建议）——与评审问题级别共用
:RuleStatus                  ← 受控词表（draft|reviewed|active|deprecated）——规则生命周期
关系：:ruleNeeds→RuleKnowledgeNeed ｜ :ruleHasCondition→RuleCondition
      :ruleHasCheck→RuleCheck ｜ :checkProduces→CheckResult
      :ruleAppliesTo→(章节/文档类型/系统等级) ｜ :resultEvidencedBy→Evidence
```

**设计要点**
- **条件与判定式分离**：条件=业务语义（可人读、可评审）；判定式=实现（可替换、可测试）。
- **知识需求显式化**：规则的"要抽取什么"必须有契约（需求 block 92 的落地）——**草案**用类 `RuleKnowledgeNeed`，**D2 之后改为数据属性 `knowledgeNeed`**（见下方修订块）；它同时是**技能 S4 的输入**。
- **结果留痕**：`CheckResult` 带证据/置信度/人工确认 → 满足"问题需 ≥1 专家核实"。
- **生命周期**：规则本体也是被运维对象（升级/退役 = §1.3）。

> **⚠️ D2 裁决后的修订（2026-10-01 你已拍板）**：上面这套**新类先不建**。理由：规则元数据只补**少量数据属性**、且只补**本 POC 需求本身要求**的；是否需要新增本体（含 `RuleKnowledgeNeed` / `RuleCheck` / `CheckResult` 等），**等双闭环技能跑完后，用本 POC 需求的领域建模来判定**。
> **P2 的实际动作**（最小化）：
> - 只加 **1 个数据属性**：`knowledgeNeed`（"判定该规则前必须先提取哪些知识"，对应需求 block 92 与 S4 的输入契约）；
> - 其余用**已有**能力承载：`ruleScope`（适用范围）、`ruleImplementation`（实现方式，可写"图查询/规则表/py"）、`ruleReference`（参考规范）、`EnforcementLevel` —— **新版需求共 4 档：严格执行 / 授权覆盖 / 建议 / 总结**；现有 TTL 只有 `bmm:Strict/Override/Advisory` → **P2 补 1 个个体 `bmm:Summary`（总结）**（R3 合理性规则用）；
> - **判定式本体**（cypher/py/表）落**领域模型库**的规则条目页，不新增类；**验证报告**同样落领域模型库（设计闭环证据）。
> - **2026-10-01 追加（闭环一/二的溯源地基）**：为"**知识来源＝智能体会话**"，P2 还要补 **`bmm:KnowledgeSession`（类）/ `bmm:SessionStatus`（词表）/ `bmm:sourceSession`（对象属性，`owl:Thing → KnowledgeSession`）/ `bmm:sourceLocator`（数据属性）**，可选 `bmm:sessionFor`。**连同 `bmm:Summary`，P2 对 bmm 的增补合计 = 6 项（5 必做 + 1 可选）**，详见 `docs/cases/技术方案评审/two-loops-framework.md` §4.4。
> - **不做**：`RuleCondition` / `RuleKnowledgeNeed` / `RuleCheck` / `CheckResult` / `RuleStatus` 等新类 —— 留待双闭环技能产出"确有必要"的结论后再加（避免本体膨胀）。

### 3.2 双轨 A/B（验证"本体规范到底值不值"）

> **对照口径（按你的反馈修正）**：A/B **只用重点规则**（R1 最低部署与灾备 / R2 开源认证）——"轨道 A 纯 NL"与"轨道 B 本体化"判的是**同一条重点规则**；**一般性规则（G1-G4）与总结级（R3）不进 A/B**（它们走 LLM + 知识库事实核查，见 §2）。A/B **等测试案例（P3 素材）就绪后再跑**（P5）。

| | **轨道 A：纯自然语言** | **轨道 B：本体规范化** |
|---|---|---|
| 知识准备 | 无（直接把规则 + 文档片段给 LLM） | 先按 `knowledgeNeed` 抽取结构化知识（图/表/文），落 L1 |
| 判定 | LLM 按规则语义判断 | 图查询/规则表/py 判定（+ LLM 仅做解释） |
| 证据 | 引用原句（可能不稳） | 结构化证据 + 坐标 + 置信度 |
| 期望 | 快、覆盖广、**不确定** | 慢一些、**确定**、可复算、可审计 |

**对照指标（PoC 前固定，避免事后挑指标）**

| 指标 | 定义 | 期望方向 |
|---|---|---|
| 判定一致率（确定性） | 同输入重复 N 次（N≥5）结论一致的比例 | B ↑↑ |
| 准确率/召回 | 对照人工黄金集（3 份方案 × 2 规则） | B ≥ A |
| 误报/漏报 | 同上 | B ↓ |
| 证据可复核率 | 结论能被第三方按证据复算的比例 | B ↑↑ |
| 人工修改率 | 专家核实中被改/驳回比例 | B ↓ |
| 成本 | 单份方案耗时 / token | A 更优（记录下来，作为**权衡依据**） |

**"何时值得本体化"的结论式判据（PoC 后产出）**：当规则满足 *条件可枚举 + 知识可抽取 + 判定需跨对象比较*（J1/J3/J5）→ 本体化收益显著；当规则本质是**裁量/风格判断**（J 全不中）→ 保持 NL。

### 4.2 会话知识溯源（**知识来源＝智能体会话**）｜重构版（2026-10-01 你已定方案）

**问题**：需求起始只有一份文档，之后**智能体交互会不断澄清/修订需求**，闭环二还会产出**改进建议**。若不把"来源"物化成知识：① 知识页"无原文依据"（`audit_scan` F3 报红）② 说不清某结论出自**哪次会话/哪一版文档** ③ A/B 样本不可复现 ④ 设计闭环断链。

**结论（你的口径）**：**知识的产生与变化都发生在与智能体的会话里** → **把"智能体会话"作为统一的知识来源**；会话在 WeKnora 里虽有保存，但**被删就断链** → **必须作为知识写进知识库**。即使从文档开始提取，也**经由会话产生**，来源同样指向**会话知识页**。

**三种页**（详见 `docs/cases/技术方案评审/two-loops-framework.md` §4）

| 页 | 内容 | 规则 |
|---|---|---|
| **会话起始页** | 只放基本信息的"会话名片"：`会话编号`｜`名称`｜`智能体名称`｜`租户名称`｜`初始问题`｜`开始时间`｜`权威库` | **跨库时每库一份副本**；**以初始库为权威**（副本标 `isAuthoritative=false` 指回权威页） |
| **会话分页** | 该段内容摘要 + 该段产出的知识页清单；**关联同一会话编号/名称** + `分页序号` | **上下文过长 且 一组高相关知识的更新已确认完成** → 才新开分页；**与它产出的知识同库**；**切换目标库必须新建分页** |
| **知识页** | 领域知识 / 结论页 / **改进建议页** | 版本化；**"原文依据"必须引用「会话分页 + 上下文定位」** |

**存档（运维智能体）**：按"该会话各页关联的知识是否全部过期/废弃"判断 → 分页可**存档**（只改状态，不删页，溯源链保留）。

**铁律**：**任何知识页 / 规则 / 本体条目的更新都必须能回到一条"会话上下文"（`sourceSession` + `sourceLocator`）**；**"不采纳/被驳回"的建议也要留痕**（否则同一问题会被反复提）。

**本体增补（P2 一起做，共 6 项：5 必做 + 1 可选）**：`bmm:KnowledgeSession`(类)｜`bmm:SessionStatus`(词表 active/archived)｜`bmm:sourceSession`(对象属性，`owl:Thing → KnowledgeSession`)｜`bmm:sourceLocator`(数据属性：分页序号+轮次/段落)｜（可选）`bmm:sessionFor`(`KnowledgeSession → CourseOfAction`)；另加前两项 `bmm:Summary`（总结档）、`knowledgeNeed`。

**用现有能力落地（零新代码即可跑）**

| 需求 | 现成能力 |
|---|---|
| 页面版本化 | `save_knowledge`（`version+1` + 版本快照；`domain_modeling` 已如此） |
| 跨上下文引用"先登记后写" | `link_candidates` → `list_link_candidates` → `resolve_link_candidate(confirm)` |
| 类型迁移留依据 | `retag_preview/apply/rollback`（每次带 ticket） |
| 无来源检测 | `audit_scan`（F3：页面无原文依据） |
| 变更 → 本体迭代 | **设计闭环**（D1）：会话页/建议页 → 迭代方案 + 验证报告 → 领域模型库 |
| 历史快照参照 | `state/context_map/history/*.json`（既有机制） |

**（已取代）上一版的 `requirement_change_log` 技能方案不再单建**：澄清 / 变更 / 改进建议的登记**统一由「会话知识页 + `sourceSession` / `sourceLocator`」承载**；条目级分类（`sessionKind`：需求澄清｜领域建模｜效果评估｜改进建议；`adviceCategory`：本体类｜技能类｜工具类｜知识类；`adviceStatus`）按框架文档 §5 处理 —— **是否独立管理/建分类，待你裁决（选项 A/B/C）**。

**与 A/B 的关系**：A/B 报告必须标注"**基于哪次会话 + 第 N 版知识**"，否则结论不可复现。
