## 0. 一句话

手机银行的**注册**与**实名认证**只负责「采集 + 核实」客户身份**三要素**；客户主数据以三要素为唯一性依据归集到
**企业级客户信息系统（ECIF）**；**签约**在此之上建立「客户-账户-渠道」的授权、限额与协议关系；**行为记录**是渠道侧的过程数据，不属于客户主数据。

## 1. 系统与角色边界（后续要落成「后台服务」）

| 系统 / 服务 | 本次职责 | 初判维护的属性 | 角色 |
|---|---|---|---|
| 手机银行 App（前端） | 采集录入、展示、客户交互 | 无（不落库） | 外部用户/客户 |
| 手机银行用户管理服务 | 注册、登录凭据、短信验证、设备绑定、渠道签约 | 手机号码、姓名（注册快照）、登录密码/指纹、设备指纹、渠道开通标志、限额 | 渠道侧（Channel） |
| 企业级客户信息系统 ECIF | 客户主数据：三要素、客户编号、联系方式、地址、职业等 | 姓名、证件种类、证件号码、客户编号、联系电话、地址、电子邮箱、职业、客户风险等级 | 企业主数据（System of Record） |
| 实名认证（联网核查）服务 | 三要素一致性核查，返回核查结论与流水号 | 核查结果、核查流水号、核查时间（**不落三要素副本**） | 外部/行内共享能力 |
| 核心系统 / 账户服务 | 客户名下账户与余额 | 账号、账户状态、卡号 | 企业主数据 |
| 渠道行为日志服务 | 行为记录：注册、登录、认证、签约、交易、设备变更 | 行为 ID、客户/用户、行为类型、时间、设备指纹、结果 | 渠道侧过程数据 |

## 2. 需求正文（约 500 字）

### R1 客户开通手机银行与实名验证

客户在手机银行 App 自助开通服务，须先**注册**：录入手机号码与姓名，用短信验证码核实号码，未解绑前一个号码只能绑定一个用户。注册后进入**实名认证**：客户须提供**姓名、证件种类（居民身份证、护照等）、证件号码**，系统调用实名认证（联网核查）服务核实三要素是否一致、证件是否有效；三要素完全一致方可通过，任一项不符或核查不可用时拒绝开通并提示到柜面办理，同时记录失败原因与核查流水号。三要素相同即同一客户，是客户信息的唯一确定依据：客户信息以三要素为锚归集至 ECIF 并分配客户编号；核实通过前只能保留待认证的注册用户，不得建立正式客户编号。此外可采集补充信息（性别、出生日期、地址、电子邮箱、职业等），并记录注册、登录、认证等行为日志。

### R2 手机银行签约

实名认证通过后，客户对拟开通的账户与服务进行**签约**：选择本人名下账户（本行借记卡/信用卡；他行卡须先验证账户），逐项签署《手机银行服务协议》并配置渠道权限与限额（转账限额、理财与基金风险测评、消息通知、设备绑定）。签约以客户三要素为准关联账户与协议：同一渠道下同一账户只允许一条有效签约，重复提交视为幂等成功，返回已存在的签约结果。签约结果写入手机银行用户管理服务，并同步 ECIF 的「客户-账户」关系与渠道开通标志；签约变更（限额调整、换绑设备、解约）必须留存变更记录与时间戳，供审计追溯。


## 3. 采集 / 核实要素清单（需求分析的第一手材料）

**3.1 注册采集（渠道侧）**

| 要素 | 采集方式 | 核实方式 | 备注 |
|---|---|---|---|
| 手机号码 | 客户录入 | 短信验证码 | 登录凭据；未解绑时一个号码一个用户 |
| 姓名 | 客户录入 | 仅格式校验（**不核实**） | 实名后由三要素核查结果覆盖 |
| 登录密码 / 生物特征 | 客户设置 | 本地校验 | 渠道凭据，**不进 ECIF** |
| 设备指纹 | 自动采集 | — | 用于设备绑定与风控 |

**3.2 实名认证（采集 + 核实，三要素）**

| 要素 | 是否三要素 | 采集 | 核实（联网核查） | 归属（主数据） |
|---|---|---|---|---|
| 姓名 | ✅ | 客户录入 | 与证件库比对 | ECIF |
| 证件种类 | ✅ | 客户选择 | 枚举合法 + 与号码匹配 | ECIF |
| 证件号码 | ✅ | 客户录入 | 与证件库比对 | ECIF |
| 证件有效期 / 发证机关 | — | 客户录入（可选） | 是否在有效期内 | ECIF |
| 核查结论 / 核查流水号 / 核查时间 | — | 核查服务返回 | — | 渠道 + 审计留痕 |

**3.3 其他客户基本信息（可采集，非三要素）**

性别、出生日期、联系地址、电子邮箱、职业、工作单位、客户风险等级（内部评定，不由客户录入）。

**3.4 行为记录（渠道过程数据，非主数据）**

注册、登录、密码重置、实名认证（成功/失败）、签约/解约、限额调整、设备换绑、交易；
每条含 `行为ID / 用户或客户 / 行为类型 / 结果 / 时间 / 设备指纹 / 来源IP`，**只追加、可审计**。

## 4. 唯一性约定（写成函数依赖的雏形，供第 4 步验证）

| 编号 | 口语表述 | 形式化（草案） | 说明 |
|---|---|---|---|
| `U1` | 三要素唯一确定客户 | `姓名,证件种类,证件号码 → 客户` | 需求明文；映射到 `easvc:FunctionalDependency` + `hasDeterminant×3` / `hasDependent` = 客户记录 |
| `U1′` | **（待验证）三要素是否为最小决定集** | `证件种类,证件号码 → 姓名` | 若成立，则 `U1` 的 determinant 里「姓名」是冗余决定属性 → 规范化/最小覆盖问题（FD 分析的第一个切入点） |
| `U2` | 手机号码 → 手机银行注册用户 | `手机号码 → 手机银行用户`（限「未解绑且已验证」） | 部分依赖/条件唯一性：解绑后号码可被他人重新注册 → 需带状态口径 |
| `U3` | 一次有效签约唯一 | `客户,账户,渠道 → 签约记录` | R2 的幂等键来源；重复提交幂等成功 |
| `U4` | 客户编号由 ECIF 分配 | `客户 → 客户编号` | 决定方向：三要素 → 客户 → 客户编号（**不得用客户编号反推三要素之外的语义**） |
| `U5` | 行为记录不唯一确定客户 | `行为ID → 行为记录`（`客户 → 多条行为`） | 多值依赖，属过程数据，**不得进主数据** |

## 5. 已知的「双维护 / 紧耦合」线索（本案例要证明的重点）

| 编号 | 属性 | 维护方 A（渠道） | 维护方 B（企业主数据） | 风险 |
|---|---|---|---|---|
| `L1` | **姓名** | 手机银行用户管理服务（注册时客户自行录入，可能昵称/错字） | ECIF（实名后以证件姓名写入） | 同一属性两处维护、取值可能不一致 → 登录展示与主数据不符 |
| `L2` | **联系电话（手机号码）** | 手机银行用户管理服务（登录标识 + 短信通道） | ECIF（联系方式） | **同值不同语义**：换号时两边不同步即造成短信发错人或登录失效 |
| `L3` | 证件种类 / 证件号码 | 手机银行**不应自存**，仅存核查结果与 `核查流水号` 引用 | ECIF（唯一权威） | 渠道留存副本 → 泄露面扩大、副本过期 |
| `L4` | 行为记录 | 渠道行为日志服务 | （不应进 ECIF） | 误当客户属性 → 主数据膨胀、隐私越界 |
| `L5` | 签约限额 / 客户风险等级 | 手机银行用户管理服务（限额） | ECIF（风险等级） | 跨服务约束：限额必须受风险等级约束（S5 类规则：规则约束的属性必须出现在契约输入/输出里） |

## 8. 待确认问题（给需求方，先答这几条再往下走）

1. **三要素是否唯一且不可变**？改姓名（如更正错字、婚姻变更）后是否仍指向同一客户？——决定 `U1` 是 `strict` 还是需带时间口径（对应 FD 的 `dependencyType`）。
2. **手机号码到底是「客户联系方式」还是「渠道账号」**？（决定 `L2` 拆分方向：若换号不应改变客户身份，则号码属渠道登录标识，联系方式另有 authoritative 源）
3. 一名客户是否允许**多个手机银行用户**（如两个手机号）？——影响 `U2` 的基数与幂等键设计。
4. 他行卡签约是否需要**四要素/五要素**（增加银行卡号、预留手机号）？——会出现新的 FD（`客户,卡号 → 签约`）。
5. 行为记录**保留期限**与是否允许关联到三要素（隐私合规）。
