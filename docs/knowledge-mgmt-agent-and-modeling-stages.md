# 企业知识管理智能体 · 建模工艺阶段（草案 v0.1｜2026-10-11｜待讨论）

> 本文回答三件事：**① 建模阶段怎么划分与声明**（含自上而下/自下而上是否两套流程、声明可调整、领域本地化）；
> **② 有哪些成熟的阶段分工与验收策略可借鉴**，并用《技术方案评审》案例给出**初始阶段 v0**；
> **③ 过程件（报告）与资产（本体约束的知识）的边界与验收口径**。
>
> 定位：**讨论稿**。落地动作（改本体 / 加技能 / 加工具 / 合智能体）在 §7 列清单，**等 §8 的裁决结果再开工**。

---

## 0 一屏（结论先行）

1. **不需要两套流程，需要「一套阶段声明 + 两套流程视图」**：自上而下与自下而上**共用中间段**（概念→本体对齐→实体化），
   差别只在**起点**（目标驱动 vs 存量驱动）与**顺序/必做项**；所以用「阶段目录（Stage Catalog）+ 流程视图（Flow Profile）」表达，
   而不是复制两份阶段定义。
2. **声明必须可版本化 + 可本地化**：三层覆盖 —— `L0 骨架`（通用，随仓库/本体走）→ `L1 领域 profile`（每个领域知识库一份：
   子集/顺序/门槛/术语别名）→ `L2 项目覆写`（只允许改门槛与开关，**不允许改语义**）。
3. **阶段不建在本体里也能跑，但"阶段声明"本身必须是可被机器读取的资产**：v0 建议**先放仓库 yaml + 领域库声明页（entity 模式）**，
   稳定后再决定是否本体化（判据见 §4.4）。
4. **过程件与资产是两种物种，不是"详细程度不同"**：过程件 = `render_mode=document`（报告/方案/评审记录/实验报告，
   用于讨论·评审·反馈·溯源·取证）；资产 = 本体约束的 entity 知识（类/关系/实例/受控词表 + 证据指针，**参与机器判定**）。
   现有落库链路**已经**有这条硬边界（文档类未带 `wiki_content` 会被 `skipped_document_nodes` 拦下），§6 把它升级成工艺纪律。
5. **阶段 v0 = 9 段 + 1 条横切治理**（§5）：启动段 `S0 存量盘点 / S1 范围目标 / S2 场景能力`、建模段 `S3 概念术语 / S4 本体对齐 /
   S5 实体化落库`、交付段 `S6 过程件 / S7 智能体·技能·工具开发 / S8 评估验收`，横切 `G 治理（巡检·建议·版本）`。

## 3 目标形态：**一个智能体**（企业知识管理）承载"领域建模 + 设计开发"

```
企业知识管理（领域建模与业务智能体设计开发）        ← 1 个智能体（替代 modeler + dev）
├─ 技能面（skills/，各自带 stages:）              ← 建模工艺的实现体
│   ├─ 启动/对齐：model_recommendation、session_provenance
│   ├─ 建模：domain_modeling、structured_modeling、multimodal_extraction
│   ├─ 设计开发：skill_development
│   ├─ 运行/评估：document_review、tech_review_extraction、revision_trace
│   └─ 规划新增：**stage_catalog（阶段目录与流程视图的下发/维护）**
├─ 工具面（MCP，按阶段分组，共 37 个 + 可选新增）   ← §7-5 给分组与收口
└─ 知识库归属
    ├─ 【企业知识管理领域】= 本智能体的**技能/工具/阶段声明**的登记与定义库（entity 模式）
    └─ 【领域知识库】     = 建模**产出**的落地库（资产 + 过程件都在这里，但模式不同，见 §6）
```

**三条边界（沿用既有裁决，不改）**：
1. **本体库手工维护**：本智能体**不改本体**；缺类/缺属性 → 写**改进建议**（`adviceCategory=本体类`），走闭环二。
2. **共享概念模型只读**：跨库概念与映射由运维智能体维护。
3. **工作知识库不做定义**：业务运行产物不回流为领域定义（要回流必须重新走 `S5` 实体化）。

**为什么能合**：`modeler` 与 `dev` 的**工具面已经相同**；差异本来就在技能里（"一个入口、按技能做事"）。
合并=消掉两个提示词之间的重复约束，把差异下沉到**技能 + 阶段路由**，避免"同一句约束写两遍、改一处漏一处"。

## 4 Q1：阶段怎么划分与声明

### 4.1 三个候选方案（各自代价）

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| **A 两套流程** | 自上而下、自下而上各写一套阶段 | 各自贴合 | 概念立即分裂（同一个"概念化"两处定义）；改一处漏一处；无法回答"两个工艺在同一阶段是否等价" | ❌ |
| **B 只声明阶段、不管顺序** | 一张无序阶段清单，顺序靠技能/提示词临场决定 | 最省事 | 顺序不可验收（"该先本体对齐还是先实体化"会漂）；评估无法定位到阶段 | 🔶 过渡可用 |
| **C 一套阶段声明的目录 + N 个流程视图**（推荐） | **Stage Catalog**＝阶段的**内容与验收**（稳定）；**Flow Profile**＝**有序子集 + 门槛参数**（可多变） | 自上而下/自下而上只是**两个 Flow**；声明可版本化；领域只改 profile | 需要一张 `stageId` 词表 + 一次对齐（技能 `stages:` 与工艺阶段的映射） | ✅ **建议 v0 用 C，且阶段先取 B 的宽松度（顺序写在 profile 里，不写进目录）** |

### 4.2 阶段目录（Stage Catalog）：每条阶段声明什么

| 字段 | 含义 | 例（`S3`） |
|---|---|---|
| `stageId` | **稳定 slug**（不改名；改名＝新阶段+迁移） | `s3-concept-terms` |
| `name` / `intent` | 一句话目的 | 概念与术语：把材料里的概念收成**受控术语**并定边界 |
| `inputs` | 需要什么才能开始 | 材料（文档/表格/图）、范围与目标（`S1` 产物）、现状盘点（`S0` 产物，自下而上时） |
| `outputs` | **过程件**与**资产**分开列 | 过程件：概念清单页；资产：术语个体 + 受控词表条目 |
| `entryCriteria` / `exitCriteria` | **可检查断言**（见 §5，全部落在现成工具上） | 出口：每个术语有定义+别名+来源；`audit_scan(scope=similar)` 无同名/近重复未裁决项 |
| `gate` | 门禁工具/id | `ontology_types`、`audit_scan`、`dry_run→apply`、人裁决 ticket |
| `roles` | 谁做（机器/人，以及"人必须确认的点"） | 智能体产出 → **人确认术语与边界** |
| `modes` | 支持哪些工艺 | `top-down / bottom-up / both` |
| `optionality` | 必做 / 条件必做 / 可选 | 条件必做（有新概念时） |
| `artifactKind` | 产物物种 | `process`（过程件）/ `asset`（资产）/ `both` |
| `evidence` | 必须带的溯源字段 | `source_refs`（L3 指针 / 会话编号 / bbox 坐标） |
| `version` | 声明版本（改语义→+1；改门槛→profile 改） | `1` |

> 与技能 `stages:` 的关系：**阶段目录是"工艺"，技能 `stages:` 是"工序"**。两者需要一张**映射表**（§7-1），
> 不允许出现"技能里有个 `extract`，但不知道它在工艺第几段"这种情况。

### 4.3 本地化与版本化：三层覆盖（"支持不同领域本地化"的答案）

| 层 | 位置 | 允许改什么 | 不允许 |
|---|---|---|---|
| **L0 骨架**（通用） | 仓库（`docs/` + `ontology/`），随版本走 | 只由我们改（走评审） | 领域/项目不能改 |
| **L1 领域 profile** | **每个领域知识库一份**（落"领域知识库"的声明页，entity 模式） | ① 阶段**子集**（某领域没有 `S4` 就不用）② **顺序**③ **门槛数值**（如 unknown 率上限）④ **术语别名/本地叫法** ⑤ 每段产物落哪个子目录 | 改阶段的**语义/出口断言** |
| **L2 项目覆写** | 项目页（白名单字段） | 必做开关、门槛数值、评审人 | 同上 |

**版本与变更治理**（复用现成机制，不新造）：
- 声明页带 `stageCatalogVersion` / `flowProfileVersion`；**变更 → 版本+1 + 变更记录**（会话页 + `wiki_page_revisions`）。
- 变更要留**影响面**：哪些技能/工具/既有建模产物受影响 → 用 `context_scan` / `audit_scan` / `retag_preview` 出影响面，
  **人确认**后生效（与 `retag_*` 两段式同款纪律）。
- 声明页自身**引用完整性**由巡检保（新增 kind 见 §6.4）。

### 4.4 "要不要把阶段建进本体"？（用既有判据，不拍脑袋）

对照 `knowledge-ops-strategy.md` 的 J1–J7：

| 判据 | 阶段声明 | 判断 |
|---|---|---|
| J1 推理确定性 | 阶段是**工程约定/配置**，不是"事实" | ✗ |
| J3 需比较/计算 | 不需要跨实例计算 | ✗ |
| J5 机器可执行 | 技能/工具**要读**它（但读的是**声明的文本**） | ⚠️ 边际 |
| J7 生命周期稳定 | **会不断调整**（你自己的原话） | ✗ |

**结论（建议 v0）**：**阶段声明不进本体**，用「仓库 yaml（单一真源，受 git 管）+ 领域库声明页（entity 模式快照，可溯源、可下发）」；
**等 §5/§6 跑过两三个领域、阶段真的稳定了**，再按 J 判据复核是否升级为本体类（如 `agent:Stage`）。
> 乐观侧：这样**零本体改动**就支持"声明不断调整 + 领域本地化"，符合你那套"越界规则"的纪律。

## 5 Q2：成熟的分工/验收参考 → 我们的**阶段 v0**

### 5.1 借鉴什么、裁掉什么

| 参考体系 | 它解决的问题 | **我们采用的形式** | 裁剪/不采用 |
|---|---|---|---|

**"两套流程"如何落成同一套阶段（这是 Q1 的直接答案）**：

```
自上而下（目标驱动）：S1 → S2 → S3 → S4 → S5 → S6 → S7 → S8
自下而上（存量驱动）：S0 → S3 →（S4）→ S5 → S1′ → S2′ → S6 → S7 → S8
                          ↑ 中间段完全相同：S3 概念 → S4 本体对齐 → S5 实体化
                          （S1′/S2′ = 由归纳结果**反向补齐**目标与能力，产物标 `provenance=derived`，必须人确认）
```
- 差别只有三处：**起点**（`S1` vs `S0`）、**顺序**（补目标在实体化之后）、**必做项**（`S4` 只在"表达不了"时走）。
- 因此**声明一套阶段、两个 Flow Profile**；领域本地化＝改 profile 的子集/顺序/门槛（§4.3）。

## 6 Q3：过程件 与 资产 —— 两种物种，硬边界

### 6.1 判别表（记住这一张就够）

| 维度 | **过程件**（process） | **资产**（asset） |
|---|---|---|
| 本体渲染模式 | `render_mode=document`（文档类） | entity（**非** document 类） |
| 落库方式 | `save_knowledge(stage="report")`，**必须带 `wiki_content` 整篇正文** | `save_knowledge(stage="graph")`（节点/关系/实例）+ 正文 |
| 谁读它 | **人**（讨论/评审/反馈/取证） | **机器**（技能、工具、规则判定、聚合、巡检） |
| 参与机器判定 | ❌ **绝不**（它可以被"引用为证据"，但不能被"当作事实来源得出结论"） | ✅ 唯一判定依据 |
| 生命周期 | 随讨论迭代、可废弃、可多版本并存 | 稳定；改动要走版本/迁移（`retag_preview→apply`） |
| 门禁 | **版本化 + 证据引用 + 人签署/会话编号** | **类型在册 + 域值合法 + 唯一标识 + 有来源（无 C1）+ 无 B1** |
| 典型 | 需求、概设、详设、评审结论页、实验报告、建议单、会议纪要 | 类/关系/实例、受控词表、术语个体、目标、场景节点、`Evaluation/Metric/Advice` |
| slug 约定（建议） | `report/…`（或既有 `*/summary/<名>-vNN`） | `<模型前缀>/<类小写>/<名>`（既有约定，如 `bmm/assessment/…`） |

### 6.2 硬边界规则（v0 拟入工艺纪律）

| # | 规则 | 现在的兜底机制 |
|---|---|---|
| **R1** | 资产**必须** entity 模式；过程件**必须** document 模式且带 `wiki_content` | 已实现：文档类在 graph 阶段未带正文 → **跳过**并回执 `skipped_document_nodes` |
| **R2** | 判定/聚合/比较**只准**读资产；过程件只能作为**证据**被引用（`source_refs`） | 需工艺纪律 + 巡检（§6.4 新增 kind） |
| **R3** | 过程件里的"结论"要沉淀成资产时，**必须重新走 `S5`**（entity 落库），**不得**把 report 页直接当资产引用 | 需工艺纪律（技能提示词 + 巡检） |
| **R4** | 每个资产**必须有来源**（指向过程件或 L3 指针/坐标） | 已有：巡检 **C1**（无来源） |
| **R5** | 每份过程件**必须可复核**：版本化（`wiki_page_revisions`）+ 证据 + 评审人/会话编号 | 已有版本化；**签署**需页面字段约定 |
| **R6** | 命名与目录分开（§6.1 slug 约定），使"物种"一眼可辨 | 需约定 + 巡检可选校验 |

### 6.3 双向溯源（这就是你要的"溯源 / 取证"）

```
L3 原始载体（文档/图纸/表格/外部权威源）
   │ ①指针 + 坐标（doc_outline / grep_chunks / reference_lookup / image bbox）
   ▼
过程件（report：需求·概设·详设·评审结论·实验报告）  ── ②人评审签署（会话编号/评审人）
   │ ③"结论→事实"的提炼（重新走 S5，留 wiki_page_revisions 与 source_refs）
   ▼
资产（entity：类/关系/实例/术语/Evaluation/Advice） ── ④被技能/工具/规则消费（谁消费在 S3 已登记）
   ▲                                                   │
   └──────── ⑤反向：从资产回到"哪个过程件/哪次会话/哪张图的哪个 bbox" ──┘
```

### 6.4 巡检可以补的三条 kind（**建议但可选**，属 §8 的 D7）
